## 0. 이 문서의 존재 이유

**사고를 인지한 순간 검색할 시간은 없다.** 절차를 미리 확정해두는 것이 목적이며, 판단이 필요한 지점을 최소화한다.

> **순서 원칙: 출혈 차단 → 접근 차단 → 원인 규명 → 복구.**
> 원인을 먼저 파악하려 들지 않는다. 손실은 조사 중에도 계속 커진다.

## 1. 시나리오 A — 키 유출 의심

가장 심각한 사고다. "의심"만으로 전 절차를 실행한다. 오탐의 비용이 미탐의 비용보다 훨씬 싸다.

| 순서 | 조치 | 소요 |
| :--- | :--- | :--- |
| 1 | **킬스위치 발동** (`HALT`) — 모든 전략 정지 | 즉시 |
| 2 | **한국투자증권 API 키 폐기·재발급** — 개발자센터에서 즉시 무효화 | 수 분 |
| 3 | **계좌 비밀번호·이체 비밀번호 변경** | 수 분 |
| 4 | Secret Manager 시크릿 버전 폐기 및 신규 버전 등록 | 수 분 |
| 5 | `candela_audit` 로그 대조 — 내가 발행하지 않은 명령·체결이 있는지 확인 | |
| 6 | 유출 경로 규명 (§4 체크리스트) | |
| 7 | 모의투자 모드로 복귀 후 재검증 → 실계좌 재개 | |

> 출금 기능이 없으므로 자산 이동은 불가하다. **하지만 악의적 매매로 인한 손실은 가능하다** — 1번(킬스위치)이 2번보다 먼저인 이유다.

## 2. 시나리오 B — Public 저장소에 시크릿 커밋

**force push로 지워도 복구 가능하다.** GitHub 캐시·포크·아카이브 서비스에 남는다. 따라서 "지우기"는 대응이 아니다.

| 순서 | 조치 |
| :--- | :--- |
| 1 | **해당 시크릿을 유출된 것으로 간주하고 §1 절차를 전부 실행** |
| 2 | 그 다음에 히스토리 정리 (`git filter-repo`) — 부수 작업이지 대응이 아니다 |
| 3 | GitHub Support에 캐시 삭제 요청 |
| 4 | 차단 실패 원인 분석 — pre-commit 훅 미설치? 패턴 미탐지? 훅 우회(`--no-verify`)? |
| 5 | 스캐너 패턴 보강 후 [security_spec](security_spec.md) 갱신 |

## 3. 시나리오 C — Admin 세션 탈취 의심

| 순서 | 조치 |
| :--- | :--- |
| 1 | **킬스위치 발동** |
| 2 | Firebase Console에서 해당 사용자 세션 전체 무효화 (토큰 revoke) |
| 3 | Firestore `admin_config/settings.admins` 화이트리스트 점검 — 추가된 계정이 없는지 |
| 4 | `candela_audit` + `/admin/api/docs/save` 커밋 이력 대조 — 임의 문서 커밋·배포가 있었는지 |
| 5 | 구글 계정 비밀번호 변경 + 2FA 재설정 |
| 6 | 세션 탈취 시점 이후의 모든 커밋을 의심 대상으로 재검토 |

> Admin은 키를 보유하지 않으므로 계좌 탈취로 직결되지 않는다. 다만 **명령 발행**과 **public 저장소 커밋 + 자동 배포**는 가능하다.

## 4. 유출 경로 체크리스트

§1-6, §2-4에서 사용한다.

- [ ] `git log -p`에 시크릿이 포함된 커밋이 있는가
- [ ] `dist/` 번들에 `VITE_` 접두어로 값이 인라인되었는가
- [ ] 로그·회고 글·문서에 주문 응답 raw dump가 붙여넣어졌는가
- [ ] `.env`가 백업·클라우드 동기화 폴더에 복사되었는가
- [ ] Worker 의존성에 최근 추가된 패키지가 있는가 (postinstall 확인)
- [ ] 로컬 머신에 악성코드 징후가 있는가
- [ ] AI 에이전트 세션에서 `.env`를 읽어 외부로 전송한 이력이 있는가
- [ ] 협업 도구·이슈 트래커에 붙여넣어졌는가

## 5. 시나리오 D — 시스템 오작동 (침해 아님)

의도치 않은 매매, 무한 주문 루프, 한도 초과 등.

| 순서 | 조치 |
| :--- | :--- |
| 1 | **킬스위치 발동** |
| 2 | 현재 포지션 확인 — 필요 시 수동 청산 (증권사 앱에서 직접) |
| 3 | `candela_audit`에서 주문 시퀀스 재구성 |
| 4 | 재현 테스트를 백테스트/모의투자에서 수행 |
| 5 | **수정 후 곧바로 실계좌로 복귀하지 않는다** — 모의투자에서 최소 2주 관찰 |

## 6. 시나리오 E — 외부 의존성 장애

증권사 API 장애, 시세 피드 단절, Cloud Run 다운 등.

*   **포지션 보유 중 우리 시스템이 죽는 것**이 가장 위험한 상태다. 손절 로직이 동작하지 않는다.
*   Worker는 시세 피드 단절을 감지하면 **자동으로 신규 주문을 중단**한다(신규 진입 금지, 기존 포지션은 유지).
*   증권사 API 장애 시 수동 청산 경로는 **증권사 앱**이다. API 복구를 기다리지 않는다.
*   배포 중에도 포지션은 살아있으므로, Worker 배포는 **장 시간 외에만** 수행한다.

## 7. 연 1회 훈련

절차는 실행해보지 않으면 작동하지 않는다.

*   모의투자 계좌에서 **킬스위치 실제 발동** → 정지까지 걸린 시간 측정
*   API 키 재발급을 실제로 1회 수행 → 소요 시간과 막히는 지점 기록
*   결과를 본 문서에 반영하고 version을 올린다

> **최초 훈련은 실계좌 전에**: 위 훈련의 첫 1회는 **실계좌 소액 진입(P5) 전에 반드시 완료**한다. 킬스위치는 P4에서 실배선되므로([ui_specification §2](ui_specification.md)), 배선 직후 모의투자에서 실발동 훈련을 1회 마친 것을 실계좌 승격 게이트로 삼는다([roadmap §2](roadmap.md)). 검증 안 된 정지 버튼으로 실자산을 운용하지 않는다.
