> 작성일 2026-11-16 · 대상: 오너(검토·승인용) · 상태: 제안
> 관련: [mvp_build_plan](mvp_build_plan.md) · [deploy_runbook](deploy_runbook.md)

## 1. 왜 지금 "초대제"인가 (배경)

냉정한 진단: **기술은 돌아가지만, 전면 공개는 이르다.** 이유는 넷이다.

1. **QA가 오너 1인 도그푸딩이 전부** — 다중 사용자·실제 모바일·에러/빈 화면/첫 사용자 경로 미검증. (오늘 발견한 프로덕션 버그 3개도 전부 "실제로 눌러보니" 나왔다.)
2. **민감 데이터인데 약관·개인정보 고지가 불명확** — 사용자가 매우 사적인 결정을 적는다.
3. **AI 비용·남용 노출** — 체험 AI는 공유 Groq 무료 키. 다수 유입 시 전역 쿼터 소진 위험.
4. **위기/정신건강 안전장치가 얇다** — 핫라인 가드레일은 최소 수준.

**초대제(신청 -> 관리자 승인 -> 초대 메일 -> 승인자만 체험)는 이 중 2·3을 구조적으로 막고, 1을 안전한 범위에서 드러낸다.** 전면 공개 대신 아는 사람 소수로 시작해, 실사용 피드백을 받으며 나머지를 보강한다.

---

## 2. 목표 (무엇을)

- 통제된 범위(승인자만)에서 **실사용 피드백과 버그를 안전하게 수집**한다.
- 관리자가 **인원과 속도를 직접 조절**한다(한 번에 소수 승인 -> 관찰 -> 추가).
- 신규 인프라 없이 **기존 자산 재사용**(Admin 페이지·Auth·Firestore·메일 엔진).

범위 밖(이번 베타에서 안 함): 경험담 커뮤니티(M2), 전면 공개, 결제.

---

## 3. 어떻게 (흐름)

### 사용자 여정
1. 소개 페이지 `/waymark`에서 **"체험하기"** 클릭
2. **Google 로그인** (+ 약관·개인정보 **동의** 체크)
3. 앱 진입 시 **"승인 대기 중"** 화면 표시
4. (관리자 승인 후) **초대 메일** 수신 -> 재방문 -> **체험 시작**

### 관리자 여정
1. Admin 페이지에 **"Waymark" 탭** 신규
2. **신청(대기) 목록** 확인 -> 각 신청 **승인 / 거절**
3. 승인 시 자동으로 **초대 메일 발송** + 상태 변경

### 상태 흐름
`신청(pending) -> 승인(approved) -> 체험 가능`
또는 `신청(pending) -> 거절(rejected) -> 접근 불가`

---

## 4. 만들 것 (작업 분해)

| 단계 | 내용 | 왜 | 담당 |
|---|---|---|---|
| P1 | **데이터 모델 + 서버 게이트** — `waymark_users`에 상태 필드 추가, 모든 Waymark API가 `approved`만 통과 | 우회 불가한 진짜 게이트 | 클로드 |
| P2 | **승인 API (관리자 전용)** — 대기 목록 조회, 승인/거절, 승인 시 초대 메일 | 관리자가 통제 | 클로드 |
| P3 | **Admin "Waymark" 탭** — 대기 목록 UI, 승인/거절 버튼 | 운영 화면 | 클로드 |
| P4 | **랜딩 "체험하기" + 대기 화면 + 동의** — 신청 진입점, 승인 대기 안내, 약관 동의 | 사용자 진입 + 프라이버시 | 클로드 |
| P5 | **A3 E2E 육안 점검** — 신청~승인~체험 전 경로, 에러/빈 화면 | 승인 유저가 깨진 화면 보면 안 됨 | 클로드 + 오너 확인 |

> P5(E2E 점검)는 **첫 승인(실유저 입장) 전에 반드시** 끼운다.

---

## 5. 반드시 지킬 3가지 (안전장치)

1. **서버 게이트 필수** — 화면만 숨기면 API 직접 호출로 우회된다. `requireAuth` 단계에서 `approved` 아니면 거절.
2. **승인은 관리자 인증 필수** — 기존 `admin-api.mjs`의 역할 검증(super_admin) 재사용. 아무나 승인 못 하게.
3. **약관·개인정보 동의를 신청 시점에** — 민감 데이터 수집의 법적·윤리적 최소선. 동의 시각 기록.

---

## 6. 공개(승인) 전 체크리스트

- [ ] 서버 게이트 동작(미승인 계정 API 차단) 확인
- [ ] 관리자 승인/거절 + 초대 메일 실제 발송 확인
- [ ] A3 E2E: 신청 -> 대기 -> 승인 -> 체험 전 경로, 에러/빈 화면 점검
- [ ] 약관·개인정보 문구 확정 및 동의 UI 연결
- [ ] 위기 가드레일 문구·범위 검토(핫라인)
- [ ] (권장) 정식 앱 아이콘 교체(현재 placeholder)

---

## 7. 오너가 해줄 것

- **약관·개인정보 처리방침 문구 확정** (초안은 클로드가 제안 가능, 최종 문구·법적 판단은 오너)
- **위기 대응 범위 결정** (어디까지 안내할지)
- **승인 운영** (누구를, 몇 명씩 승인할지)
- GCP/시크릿 추가 작업은 이번 범위에선 **불필요**(배포·메일·인증 이미 구축됨)

---

## 8. 데이터 모델 (참고)

`waymark_users` 문서에 필드 추가:

| 필드 | 값 | 의미 |
|---|---|---|
| `accessStatus` | `pending` / `approved` / `rejected` | 접근 상태 |
| `requestedAt` | 시각 | 신청 시점 |
| `approvedAt` | 시각 | 승인 시점 |
| `rejectedAt` | 시각 | 거절 시점 |
| `tosAgreedAt` | 시각 | 약관·개인정보 동의 시점 |
| `inviteSentAt` | 시각 | 초대 메일 발송 시점 |

별도 컬렉션 대신 기존 문서에 필드로 두어 단순하게 유지.

---

## 9. 순서 제안

```
P1 서버 게이트/모델 -> P2 승인 API -> P3 Admin 탭 -> P4 랜딩/대기/동의 -> P5 E2E 점검 -> 첫 승인(소수)
```

각 단계는 독립적으로 커밋·배포 가능. 사용자 비노출 상태로 쌓다가, **P5 통과 후에만 첫 실유저를 승인**한다.

---

## 10. 이 베타가 해결 / 미해결

- 해결: **AI 비용·남용**(승인 인원만 소비), **통제 롤아웃**(인원·속도 조절), **프라이버시**(동의 추가 시)
- 미해결(병행 보강): **위기 안전장치 심화**, **다국어·다기기 폭넓은 QA**(승인 늘리며 관찰)

---

## 한 줄 결론

**접근 방식은 견고하다. 5·6의 안전장치만 지키면, 지금 바로 초대제 베타로 사용자에게 열어도 무방하다** — 단, 첫 실유저 승인은 A3 점검 통과 후.
