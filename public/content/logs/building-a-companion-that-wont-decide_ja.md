# 代わりに決めないと約束して、AIを載せました

ch.14で、Waymarkが守るべき一つとして「代わりに決めない」と書きました。あのときは宣言でした。体験版を作る過程で、その一文がもっとも多くのコードを書かせた条項になりました。

伴走者にAIを載せることにしたからです。LLMは問われれば答えます。「どちらがいいか」と聞けば選びます。宣言を守るにはその既定の性質を抑える必要があり、抑える作業はプロンプト一行では終わりませんでした。

## 1. 範囲は削りましたが、AIは削りませんでした

着手前に企画書7点を読み直し、範囲を削りました。機能10個のうち3個を後ろへ回しました。回したのは経験談のレイヤーです。似た決断をした人の話を受け取り、検収し、マッチングして見せる機能ですが、提出・匿名化・通報・個人情報の検収までパイプライン全体が必要でした。

より決定的な理由は、**もっとも手をかけるべき場所がもっとも空っぽだった**ことです。経験談はコールドスタートが最大のリスクです。初期に経験談がゼロなら、ループのその枠は空虚になり、かけた労力に対する体感はもっとも低くなります。ひとりでゼロから始める状況でモデレーションのパイプラインを立てるのは、順序が違いました。

一方で伴走メッセージは**削らずに全体を入れました**。範囲を削る最中に、削らないと決めた唯一の機能です。ユーザーが実際に触るのはそれであり、それが薄くなれば残るのは決断記録のノートアプリです。削った結果は、7個を入れて3個を後回し、モデレーション0・コールドスタート0で立てるコアです。

## 2. 三つの経路が同じハードルールを通ります

伴走メッセージは一つのタイムラインに積まれますが、ソースは三つです。

| 経路 | 内容 | コスト |
| :--- | :--- | :--- |
| テンプレート5つの結 | LLMを使いません。感情・イベントの規則でトーンを選び、変数のみ置換します | 0・ネットワーク遅延0 |
| 体験AI | サーバーが当方の鍵で呼び出します。ユーザーごとに月20回ほど | 当方の費用・上限あり |
| BYOK | ユーザーが自分の鍵をつなぎます | ユーザーの費用・上限なし |

三つの経路が**同じハードルールと同じガードレールを通ります**。代わりに決めないこと、危機のサインには専門的な支援への案内、既存サービスのコーチ口調の禁止です。AIが切れていても原則は同じであるべきなので、テンプレートはフォールバックではなく既定の経路です。体験の上限を使い切ったときや鍵がつながっていないときは、静かにテンプレートへ戻ります。

一か所だけ逆に振りました。AIが先に声をかける場面です。決断を書いて詳細に入ったとき、タイムラインにテンプレート一行だけだと空いて見えます。そこで**自分の鍵をつないだ利用者にのみ**、決断の文脈をもとに最初のひと言を一度だけ生成します。本人の鍵なので当方の費用は0で、体験の上限も使いません。生成に成功すればテンプレートの行は描画時に隠して重複なく差し替え、鍵がない場合や呼び出しが失敗した場合は**静かにテンプレートをそのまま残します**。失敗を利用者に知らせない側を選びました。伴走者が「AIの呼び出しに失敗しました」と言うのは、伴走ではありません。

原則がもっともはっきり入っているのはテンプレートの結びです。5つの結のすべてが、同じ位置で決断を返します。

```
助言  どちらが正しいか、結局あなたが一番わかっています。
整理  整理は手伝いましたが、決断はあなたのものです。
検証  反対するためではありません。あなたの選択がより確かになるよう、そばで支えるだけです。
```

## 3. トーンを選ぶ規則に原則が入りました

最初はトーンが四つでした。なぐさめ・助言・応援・整理です。使っていると空いた場所が見えました。一方に傾いた決断を押してみる役が、どこにもなかったのです。助言は別の視点を差し出す側であり、前提を点検させることはそれとは別の仕事です。**検証**を五つ目の結として新設し、役割を分けました。

そのうえでトーンの自動選択を書き直しました。

```js
function defaultTone(emotionTags = [], importance = 2) {
  const s = new Set(emotionTags);
  // 不安・恐れが混じれば、まず重さを認める(相反する場合は安全側)
  if (s.has('anxiety') || s.has('fear')) return 'comfort';
  if (s.has('confusion')) return 'clarify';
  // 自信・高揚・安堵: 大きな決断(重要度3)なら「軽く」ではなく落ち着いて点検(verify)
  if (s.has('confidence') || s.has('excitement') || s.has('relief')) {
    return Number(importance) >= 3 ? 'verify' : 'cheer';
  }
  return 'comfort';
}
```

二行に判断が入っています。一つは、**大きな決断で気分がいいときには応援しない**ということです。重要度が高いのに自信や高揚がついていれば、「軽く行きましょう」ではなく「見落とした前提はありませんか」へ向かいます。応援のほうが聞こえはいいのですが、大きな決断で聞こえのいい言葉を選ぶのは、そばにいることではなく機嫌をとることです。

もう一つは、**感情が相反するときは安全な側を選ぶ**ということです。高揚と不安が一緒に書かれていれば、なぐさめへ向かいます。重さを先に認める側は、外れたときの害が小さいからです。

## 4. コードを書く前にデータ方針を見ました

外へ送る話をする前に、内側でどう置くかを先に決めました。決断の記録は、ブラウザがデータベースを直接読みません。データベースの規則はすべて拒否にし、読み書きはすべてサーバーAPI経由だけにします。サーバーはリクエストごとに認証を確かめ、その記録が**その利用者のものか**を検証します。他人のIDを入れて他人の決断を取り出す経路を、構造的になくす側です。

会員の仕組みは新しく作らず、既存のものに接ぎました。有料プランがなく課金単位が要らないので、統合アカウントのサービスを新設するより、既存の認証の利用者識別子で結合するだけで十分でした。作らなかったことも決定です。

その次が外部モデルです。他人の決断の記録を外へ送る作業です。そこで体験AIの着手に**先行条件**を置きました。提供者が学習に使わず、データを保持しないことを公式文書で確認するまでコードを書かない、というものです。既定で保持しないこと、学習に使わないこと、データ保持ゼロの設定が一部の契約顧客だけでなく全顧客に開かれていることまで公式文書で確認してから着手しました。

送る量も削りました。その決断の最小限の文脈だけを送り、識別子や他の決断は送らず、個人情報は伏せます。1回の呼び出しで送る文脈も、画面一枚ぶん程度に抑えました。

BYOKは調査の段階で結論が分かれました。利用者の鍵を当方のサーバーに入れないことが目標でしたが、提供者を全数調べると**ブラウザからの直接呼び出しを許すところが一つだけ**でした。その一つは専用ヘッダーで直接呼び出しを許すので、当方のサーバーもデータベースもまったく経由しません。残りはCORSで塞がれているため、サーバーが鍵をメモリ上でのみ受け取って即座に転送し、保存もログも残さないステートレスな通過方式にしました。同じBYOKでも**どの鍵を差すかで経路が違う**ということであり、その違いを利用者に隠さない側を選びました。鍵はブラウザに暗号化して置き、ワンクリックで消します。

そして告知を入れました。**プライバシーは、あなたの鍵の提供者とティアに左右されます。** 無料ティアが入力を学習に使う提供者では、入力時に警告を出します。保証できないことを保証すると書かないほうがよいからです。

危機のサインは両側で止めます。入力で引っかかればモデルを呼ばずに相談の案内へ差し替え、モデルが答えを返したあとにも同じ検査をもう一度通します。片側だけに置けば、二つのうち一方が漏れるからです。

## 5. 先に訪ねる側が、まとわりつかないように

Waymarkの心臓は、利用者が開かなくても先に訪ねてくることです。先に訪ねる機能は、設計を少し誤るだけでまとわりつくアプリになります。だから送る規則よりも、**送らない規則**に手がかかりました。

- **静かな時間は飛ばさず、先に延ばします。** 到来時刻が静かな時間の中なら取り消すのではなく、終了後の最初の周期で送ります。沈黙と欠落は別物です。
- **反応がなければ自ら退きます。** 2回続けて反応がなければ1回飛ばし、3回なら能動的な通知を止めます。
- **決断が閉じれば、残りの予定を取り消します。**
- **到達は二重の経路で担保します。** メールとWebプッシュを一緒に送ります。プッシュを拒否していても、iOSでホーム画面に未インストールでも、メールでは届きます。

この二重化で一日を使いました。Webプッシュが黙って届かず、サービスワーカーをビルドが触らない原本ファイルとして置き、メッセージをデータのみに切り替えてからようやく受信できました。送信ジョブでは、別のモジュールから取り込んだタイムスタンプのヘルパーが直列化されず、書き込みが失敗しました。データベースのハンドルと同じインスタンスのヘルパーを使うことで終わりましたが、原因にたどり着くまでログは何も語ってくれませんでした。

## 6. 公開ではなく、招待制で開けました

作り終えてから、全面公開はしませんでした。承認した人だけが入ります。紹介ページから申請し、規約に同意し、管理者が承認すると招待メールが届きます。

ゲートは画面ではなくサーバーに置きました。すべてのAPIが承認済みの状態だけを通します。画面だけで止めるなら、それは迂回できる案内文であってゲートではありません。さらに最初の承認の前に、申請から体験までの全経路を目で一度通す手順を挟みました。承認されて入った最初の利用者が壊れた画面を見れば、その人は二度と来ません。

開けて自分で使ってみると、直すところがまた出ました。最大のものは入力が二つに分かれていたことです。メモを書く欄とAIに尋ねる欄が別にありましたが、決断の前では書くことと尋ねることは同じ行為でした。一つにまとめました。韓国語と日本語の入力では、変換中にEnterが効いて文が半分だけ送られることがありました。変換中のガードを入れました。

答えが途中で切れて出ることもありました。ある提供者で思考の過程にトークンを使い切り、本文がトークン上限に当たって、切れた断片がそのまま吹き出しに入りました。思考機能を切り、その設定を受け付けないモデルなら一度だけ再試行し、それでも上限に当たるなら断片を捨ててテンプレートへ下ろすようにしました。話を切る伴走者は、間違ったことを言う伴走者より早く信頼を失います。

体験版はまだ承認した人だけが使う状態です。経験談のレイヤーは入っておらず、その場所を空けてあることが見えるようにもしていません。いま証明しようとしているのは一つです。先に訪ね、そばにいて、代わりに決めないことで、決断が少し孤独でなくなるのか。それが成り立つか確かめる前にコミュニティを載せれば、成り立たない理由を見つけられなくなります。
