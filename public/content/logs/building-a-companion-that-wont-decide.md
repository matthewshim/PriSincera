# 대신 결정하지 않기로 했는데, AI를 붙였습니다

ch.14에서 Waymark의 지켜야 할 한 가지로 "대신 결정하지 않는다"를 적었습니다. 그때는 선언이었습니다. 체험판을 만들면서 그 한 문장이 가장 많은 코드를 쓰게 한 조항이 됐습니다.

동반자에 AI를 붙이기로 했기 때문입니다. LLM은 물으면 답합니다. "둘 중 어느 쪽이 낫겠냐"고 하면 고릅니다. 선언을 지키려면 그 기본 성향을 막아야 하고, 막는 일은 프롬프트 한 줄로 끝나지 않았습니다.

## 1. 범위는 줄였는데 AI는 줄이지 않았습니다

착수 전에 기획서 7종을 다시 읽고 범위를 줄였습니다. 기능 10개 중 3개를 뒤로 미뤘습니다. 미룬 것은 경험담 레이어입니다. 비슷한 결정을 해 본 사람의 이야기를 받아서 검수하고 매칭해 보여주는 기능인데, 제출·익명화·신고·PII 검수까지 파이프라인 전체가 필요했습니다.

더 결정적인 이유는 **가장 공들일 곳이 가장 비어 있다**는 것이었습니다. 경험담은 콜드스타트가 1순위 리스크입니다. 초기에 경험담이 0이면 루프의 그 칸이 공허해지고, 들인 노력 대비 체감이 가장 낮습니다. 혼자 만드는 제로 상태에서 모더레이션 파이프라인을 세우는 것은 순서가 틀렸습니다.

대신 동반 메시지는 **줄이지 않고 전체를 넣었습니다.** 범위를 줄이는 중에 범위를 줄이지 않기로 한 유일한 기능입니다. 사용자가 실제로 만지는 것이 그것이고, 그것이 얇아지면 남는 것은 결정 기록 노트 앱입니다. 줄인 결과는 기록에서 7개 들어가고 3개 미룸, 모더레이션 0, 콜드스타트 0으로 설 수 있는 코어입니다.

## 2. 세 경로가 같은 하드룰을 지납니다

동반 메시지는 하나의 타임라인에 쌓이지만 소스가 셋입니다.

| 경로 | 무엇 | 비용 |
| :--- | :--- | :--- |
| 템플릿 다섯 결 | LLM을 쓰지 않습니다. 감정·이벤트 규칙으로 톤을 고르고 변수만 치환합니다 | 0 · 네트워크 지연 0 |
| 체험 AI | 서버가 우리 키로 호출합니다. 사용자당 월 스무 번 남짓 | 우리 비용 · 캡 |
| BYOK | 사용자가 자기 키를 연결합니다 | 사용자 비용 · 무제한 |

세 경로가 **같은 하드룰과 같은 가드레일을 지납니다.** 대신 결정하지 않기, 위기 신호에는 전문 도움 안내, 기존 서비스의 코치 톤 금지입니다. AI가 꺼져 있어도 원칙은 같아야 하므로, 템플릿이 폴백이 아니라 기본 경로입니다. 체험 캡이 소진되거나 BYOK가 연결되지 않았으면 조용히 템플릿으로 돌아갑니다.

한 군데는 거꾸로 갔습니다. AI가 먼저 말을 거는 자리입니다. 결정을 적고 상세로 들어왔을 때 타임라인에 템플릿 한 줄만 있으면 비어 보입니다. 그래서 **자기 키를 연결한 사용자에게만** 결정 맥락을 바탕으로 첫 한마디를 한 번 생성합니다. 자기 키라 우리 비용은 0이고, 체험 캡도 쓰지 않습니다. 생성에 성공하면 템플릿 줄은 렌더에서 숨겨 중복 없이 교체하고, 키가 없거나 호출이 실패하면 **조용히 템플릿을 그대로 둡니다.** 실패를 사용자에게 알리지 않는 쪽을 골랐습니다. 동반자가 "AI 호출에 실패했습니다"라고 말하는 것은 동반이 아닙니다.

원칙이 가장 또렷하게 들어간 자리는 템플릿의 맺음말입니다. 다섯 결 전부가 같은 자리에서 결정을 돌려줍니다.

```
조언  어느 쪽이 더 맞을지, 결국 당신이 더 잘 알아요.
정리  정리는 도왔지만, 결정은 당신 몫으로 남겨둘게요.
검증  맞서려는 게 아니에요. 당신의 선택이 더 단단해지도록 곁에서 거들 뿐이에요.
```

## 3. 톤을 고르는 규칙에 원칙이 들어갔습니다

처음에는 톤이 넷이었습니다. 위로·조언·응원·정리입니다. 쓰다 보니 빈 자리가 보였습니다. 한쪽으로 기운 결정을 눌러 보는 역할이 없었습니다. 조언은 다른 관점을 제시하는 쪽이고, 전제를 점검하게 만드는 것은 그와 다른 일입니다. **검증**을 다섯 번째 결로 신설해 역할을 쪼갰습니다.

그러고 나서 톤 자동 선택 규칙을 다시 썼습니다.

```js
function defaultTone(emotionTags = [], importance = 2) {
  const s = new Set(emotionTags);
  // 불안·두려움이 섞이면 무게를 먼저 인정(상충 시 안전측)
  if (s.has('anxiety') || s.has('fear')) return 'comfort';
  if (s.has('confusion')) return 'clarify';
  // 자신감·설렘·홀가분함: 큰 결정(중요도 3)이면 '가볍게' 대신 차분히 점검(verify)
  if (s.has('confidence') || s.has('excitement') || s.has('relief')) {
    return Number(importance) >= 3 ? 'verify' : 'cheer';
  }
  return 'comfort';
}
```

두 줄에 판단이 들어 있습니다. 하나는 **큰 결정에 기분이 좋을 때는 응원하지 않는다**는 것입니다. 중요도가 높은데 자신감·설렘이 붙어 있으면 "가볍게 가요"가 아니라 "놓친 전제는 없나요"로 갑니다. 응원이 더 듣기 좋지만, 큰 결정에서 듣기 좋은 말을 고르는 것은 곁에 있는 게 아니라 비위를 맞추는 것입니다.

다른 하나는 **감정이 상충하면 안전한 쪽을 고른다**는 것입니다. 설렘과 불안이 같이 적혀 있으면 위로로 갑니다. 무게를 먼저 인정하는 쪽이 틀렸을 때 피해가 적습니다.

## 4. 코드를 쓰기 전에 데이터 정책을 먼저 봤습니다

외부로 보내는 이야기를 하기 전에 안에서 어떻게 두는지부터 정했습니다. 결정 기록은 브라우저가 데이터베이스를 직접 읽지 않습니다. 데이터베이스 규칙은 전부 거부로 두고, 모든 읽기와 쓰기를 서버 API로만 받습니다. 서버는 요청마다 인증을 확인하고 그 기록이 **그 사용자 소유인지**를 검증합니다. 남의 아이디를 넣어 남의 결정을 꺼내는 경로를 구조적으로 없애는 쪽입니다.

회원 체계는 새로 만들지 않고 기존 것에 붙였습니다. 유료 플랜이 없어 과금 단위가 필요 없으니, 통합 계정 서비스를 신설하는 대신 기존 인증의 사용자 식별자로 조인하는 것으로 충분했습니다. 안 만든 것도 결정입니다.

그다음이 외부 모델입니다. 남의 결정 기록을 바깥으로 보내는 일입니다. 그래서 체험 AI 착수의 **선행 조건**을 걸었습니다. 공급자가 무학습이고 데이터를 보관하지 않는다는 것을 공식 문서에서 확인하기 전에는 코드를 쓰지 않는 것입니다. 기본 무보존과 무학습, 전체 고객의 제로 데이터 보존 설정 가능 여부까지 공식 문서로 확인한 뒤 착수했습니다.

보내는 양도 줄였습니다. 해당 결정의 최소 맥락만 보내고, 식별자와 다른 결정은 보내지 않고, PII는 레드액션합니다. 호출당 보내는 맥락도 한 화면 분량으로 묶었습니다.

BYOK는 조사부터 결론이 갈렸습니다. 사용자 키를 우리 서버에 들이지 않는 것이 목표였는데, 공급자를 전수 조사해 보니 **브라우저에서 직접 호출을 허용하는 곳이 하나뿐**이었습니다. 그 한 곳은 전용 헤더로 직접 호출을 허용해서 우리 서버와 데이터베이스를 아예 거치지 않습니다. 나머지는 CORS가 막혀 있어, 서버가 키를 메모리에서만 받아 즉시 전달하고 저장도 로그도 남기지 않는 무상태 패스스루로 갔습니다. 같은 BYOK라도 **어느 키를 꽂느냐에 따라 경로가 다르다**는 뜻이고, 그 차이를 사용자에게 숨기지 않는 쪽을 골랐습니다. 키는 브라우저에 암호화해 두고 원클릭으로 지웁니다.

그리고 고지를 넣었습니다. **프라이버시는 당신 키의 공급자와 티어에 달려 있습니다.** 무료 티어가 학습에 쓰는 공급자는 입력할 때 경고를 띄웁니다. 우리가 보장할 수 없는 것을 보장한다고 쓰지 않는 쪽이 낫습니다.

위기 신호는 양쪽에서 막습니다. 입력에서 걸리면 모델을 호출하지 않고 상담 안내로 치환하고, 모델이 답을 돌려준 뒤에도 같은 검사를 한 번 더 통과시킵니다. 한쪽만 두면 둘 중 하나가 새기 때문입니다.

## 5. 먼저 찾아오는 쪽이 들러붙지 않게

Waymark의 심장은 사용자가 열지 않아도 먼저 찾아오는 것입니다. 먼저 찾아오는 기능은 설계를 조금만 잘못하면 들러붙는 앱이 됩니다. 그래서 보내는 규칙보다 **보내지 않는 규칙**에 더 손이 갔습니다.

- **조용 시간은 건너뛰지 않고 미룹니다.** 도래 시각이 조용 시간 안이면 취소하는 게 아니라 종료 후 첫 주기에 보냅니다. 침묵과 누락은 다릅니다.
- **응답이 없으면 스스로 물러납니다.** 두 번 연속 반응이 없으면 한 번 건너뛰고, 세 번이면 능동 알림을 멈춥니다.
- **결정이 닫히면 남은 예약을 취소합니다.**
- **도달은 이중 채널로 보장합니다.** 이메일과 웹푸시를 같이 보냅니다. 푸시를 거부했거나 iOS에서 홈 화면에 설치하지 않았어도 이메일로는 닿습니다.

이중 채널에서 하루를 썼습니다. 웹푸시가 조용히 오지 않았는데, 서비스 워커를 빌드가 건드리지 않는 원본 파일로 두고 메시지를 데이터 전용으로 바꾸고 나서야 수신됐습니다. 발송 잡에서는 다른 모듈에서 가져온 타임스탬프 헬퍼가 직렬화되지 않아 기록이 실패했습니다. 데이터베이스 핸들과 같은 인스턴스의 헬퍼를 쓰는 것으로 끝났지만, 원인을 찾기까지는 로그가 아무 말도 해 주지 않았습니다.

## 6. 공개하지 않고, 초대제로 열었습니다

다 만들고 나서 전면 공개하지 않았습니다. 승인한 사람만 들어옵니다. 소개 페이지에서 신청하고, 약관에 동의하고, 관리자가 승인하면 초대 메일이 갑니다.

게이트는 화면이 아니라 서버에 뒀습니다. 모든 API가 승인 상태만 통과시킵니다. 화면에서만 막으면 우회되는 안내문이지 게이트가 아닙니다. 그리고 첫 승인 전에 신청부터 체험까지 전 경로를 눈으로 한 번 훑는 절차를 끼웠습니다. 승인받고 들어온 첫 사용자가 깨진 화면을 보면 그 사람은 두 번 오지 않습니다.

열어 두고 직접 써 보니 고칠 것이 또 나왔습니다. 가장 컸던 것은 입력이 둘로 나뉘어 있던 것입니다. 메모를 적는 칸과 AI에게 묻는 칸이 따로 있었는데, 결정 앞에서는 적는 것과 묻는 것이 같은 행동이었습니다. 하나로 합쳤습니다. 한글과 일본어 입력에서는 조합 중에 엔터가 먹혀 문장이 반쯤 전송되기도 했습니다. 조합 가드를 넣었습니다.

답이 중간에 잘려 나오는 것도 있었습니다. 한 공급자에서 생각 과정에 토큰을 다 쓰고 본문이 토큰 상한에 걸려, 잘린 조각이 그대로 말풍선에 들어갔습니다. 생각 기능을 끄고, 그 설정을 받지 않는 모델이면 한 번 재시도하고, 그래도 상한에 걸리면 조각을 버리고 템플릿으로 내려가게 했습니다. 말을 끊는 동반자는 틀린 말을 하는 동반자보다 신뢰를 빨리 잃습니다.

체험판은 아직 승인한 사람만 쓰는 상태입니다. 경험담 레이어는 들어가지 않았고, 그 자리를 비워 둔 것이 보이게 두지도 않았습니다. 지금 증명하려는 것은 하나입니다. 먼저 찾아오고, 곁에 있고, 대신 결정하지 않는 것으로 결정이 덜 외로워지는지입니다. 그것이 되는지 확인하기 전에 커뮤니티를 얹으면, 안 되는 이유를 찾을 수 없게 됩니다.
